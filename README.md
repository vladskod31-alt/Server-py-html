# Server-py-html

Делаю свой сервер на py html

**Нестабільний (chaos) HTTP-сервер на чистому Python** — спеціально ненадійний, щоб тренувати
клієнти на витривалість: ретраї, таймаути, обробку обірваних з'єднань. Плюс HTML-дешборд,
який у реальному часі показує, як сервер деградує.

Жодних залежностей — лише стандартна бібліотека Python 3.8+.

## Що вміє

Сервер випадково:

| режим | що робить |
|-------|-----------|
| `slow` | відповідає 200, але після затримки 1–12 с |
| `err500` | повертає `500 Internal Server Error` |
| `err503` | повертає `503 Service Unavailable` |
| `drop` | рве TCP-з'єднання, не надіславши жодного байта |
| `partial` | надсилає заголовки й половину тіла, потім обриває |
| `hang` | підвисає на 6–45 с (довше за будь-який розумний таймаут клієнта) |
| **аварія** | випадково «лягає» на 1–20 с: у цей проміжок **усі** запити отримують 503 |

Після кожної аварії є cooldown (8–40 с залежно від рівня), щоб сервер встигав ожити
й показати решту режимів хаосу.

## Швидкий старт

```bash
python3 server.py --port 8000 --level medium
```

Відкрити `http://localhost:8000/` — там живий монітор пінгу з графіком затримки,
успішністю та кнопками керування хаосом.

```bash
python3 ping_test.py --url http://127.0.0.1:8000 --count 30 --concurrency 6 --timeout 4
```

`ping_test.py` повертає exit code `0`, якщо success rate ≥ 99%, і `2` інакше —
зручно для CI-перевірки клієнта.

## Рівні нестабільності

`--level`: `off` · `light` · `medium` (типово) · `heavy` · `insane`

Перемикається на льоту:

```bash
curl -X POST http://127.0.0.1:8000/admin/chaos -H 'Content-Type: application/json' -d '{"level":"insane"}'
curl -X POST http://127.0.0.1:8000/admin/outage  -H 'Content-Type: application/json' -d '{"seconds":5}'   # примусова аварія
curl -X POST http://127.0.0.1:8000/admin/reset                                                          # скинути метрики
```

## Ендпоінти

| метод | шлях | призначення |
|-------|------|-------------|
| GET | `/` | HTML-дешборд (живий монітор) |
| GET | `/ping` | основний ендпоінт, **на ньому працює весь хаос** |
| GET | `/health` | чесний стан: `up` / `degraded` / `unstable` + метрики |
| GET | `/stats` | JSON-метрики: success rate, перцентилі, розбивка результатів |
| GET | `/admin/chaos` | поточний рівень і доступні рівні |
| POST | `/admin/chaos` | змінити рівень хаосу |
| POST | `/admin/outage` | влаштувати аварію на N секунд |
| POST | `/admin/reset` | обнулити лічильники |

## Виміряні результати

Прогін `ping_test.py --count 30 --concurrency 6 --timeout 4` на Python 3.11.2:

| рівень | success rate | помилки |
|--------|--------------|---------|
| `off` | **100%** (30/30), p95 20.6 мс | — |
| `light` | 83.3% | 500×2, 503×3 |
| `medium` | 73.3–93.3% (5 прогонів) | 500, 503, drop, timeout |
| `heavy` | 46.7% | 500×8, drop×3, 503×3, timeout×2 |
| `insane` | 30.0% | 500×9, timeout×5, drop×3, partial×2, 503×2 |

На рівнях з аваріями результат «плаває»: якщо проміжок аварії накриває увесь прогін,
success rate падає до 0%. Це не баг, а саме та поведінка, яку треба вчити клієнта переживати.

Те саме, побачене з боку `curl`:

```
200 500 500 000 exit28 200 000 exit28 000 exit52 200 exit18 503 503 503 ...
```

`exit28` — таймаут (hang), `exit52` — порожня відповідь (drop), `exit18` — обірване тіло (partial).

## Опції сервера

```
--host   адреса для прослуховування (типово 0.0.0.0)
--port   порт (типово 8000, або змінна PORT)
--level  off|light|medium|heavy|insane (типово medium, або змінна CHAOS_LEVEL)
--seed   фіксований seed випадковості — для відтворюваних тестів
```
